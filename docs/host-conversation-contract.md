# Conversation-first контракт хоста (эпик 026)

Как RAG-хост передаёт движку разговор и контекст. Правило одно: **история — это
массив реальных сообщений; всё остальное — помеченные каналы. История никогда не
пересобирается в текст.**

Урок из продакшена (MeetScript B17, 2026-07-23): хост собирал ОДИН составной
RAG-промпт, нёсший только последний вопрос. Для модели истории разговора не
существовало — «сколько из этих шести?» разрешалось по списку retrieval-источников,
а не по её собственному перечислению («0 из 6» вместо «3 из 6»). Ни движковый
`protect_recent_turns`, ни конденсация retrieval-запроса такое не чинят: они
защищают другие слои.

Референсы: hermes — «History is owned by the agent», эфемерный контекст компонуется
в `api_content` текущего хода, оригинал в `messages` не мутируется (байтовая
стабильность префикса = промпт-кэш); openclaude — полный `Message[]` как источник
правды, контекст слоями-attachment'ами, `requestOnlyMessages` для одно-запросного
фрейминга.

## Каналы

| Канал | Что кладём | Судьба |
|---|---|---|
| `AgentRunInput.messages` | РЕАЛЬНЫЕ ходы диалога: user/assistant как они были показаны пользователю (включая прошлые ответы ассистента) | durable: сеет protocol-транскрипт, участвует в чекпойнтах, защищается `protect_recent_turns` при тримминге |
| `AgentRunInput.request_only_context` | RAG-блоки (retrieved context, sources index, обзор корпуса), эфемерный стиринг | model-visible на КАЖДОМ вызове этого рана, инъецируется перед последним user-ходом, НИКОГДА не попадает в protocol-транскрипт/чекпойнт-историю |
| `system` (профиль/`system_instruction`) | стабильные инструкции роли | обычные правила системного промпта |
| `app_metadata["memory"]` | чистый вопрос для памяти (`user_text`/`recall_query`) | recall/remember работают с вопросом, а не с RAG-конвертом (эпик 021) |

## Правила

1. **Прошлые ответы ассистента — это сообщения, а не текст в промпте.** Блоки вида
   «Недавний диалог: …» внутри составного промпта — паллиатив: не кэшируются
   префиксно, соревнуются с retrieval за внимание, требуют собственных бюджетов.
2. **Retrieved-контекст помечается как справочный**, не как речь пользователя:
   в `request_only_context` кладите сообщение с явной рамкой («Справочные материалы
   по запросу — НЕ часть диалога; при конфликте приоритет у диалога»).
3. **Составной промпт допустим** только для одноходовых джобов без истории
   (суммаризация, извлечение, классификация). Цена в многоходовом чате — класс B17.
4. **Не мутируйте историю при ретраях/ревизиях**: движок сам ведёт protocol-
   транскрипт; хост передаёт одну и ту же историю за ран.
5. Бюджеты: историю капит движковый тримминг (`protect_recent_turns` держит хвост);
   `request_only_context` капится хостом (это его контент-бюджет retrieval).

## Миграция составного промпта (рецепт)

Было: `input = f"{инструкции}\n{обзор}\n{источники}\nUser question: {вопрос}\n{контекст}"`.

Стало:
- `messages = [*история_диалога, user(вопрос)]`
- `request_only_context = [user("Справочные материалы (НЕ диалог):\n{обзор}\n{источники}\n{контекст}")]`
- инструкции → `system_instruction`/профиль.

Ожидаемые эффекты: анафора на собственные ответы работает без спецблоков; префикс
(system + ранняя история) стабилен между ходами → промпт-кэш провайдера; retrieval
не «прикидывается» частью вопроса.
