# Гигиена recall памяти: релевантность, свежесть, незагрязнение

Дата создания: 2026-07-23. Статус: **proposed** (наследует открытые пункты 021).

Мотивация из живых данных (2026-07-22/23, MeetScript dev, CHAT_V2_MEMORY on):
1. Бенч-кейс `clarify_when` («когда была ТА встреча?») в свипе ответил вместо уточнения —
   recall подсунул антецедент из чужого разговора того же пользователя; в изолированном
   прогоне — PASS. Порядкозависимый флейк от загрязнения recall.
2. Живой прогон «перечисли встречи по Аргусу» начался с «Спасибо за уточнение… кроме уже
   перечисленных» — модель продолжила НЕ ЭТОТ разговор (recall стал псевдо-историей).
3. Наблюдение dd9a5ee (2026-07-19): extraction-JSON флейк deepseek → fail-open в raw-turn без
   слота → supersede не схлопывает → recall отдаёт устаревший факт. Кандидаты фикса записаны,
   ни один не реализован.
Движковый recall — только recency+keyword (`memory/provider.py:233`); ни порога релевантности,
ни свежести, ни абстейна. Семантический rerank живёт на хосте.

## Reference-first

- **openclaude `src/memdir/findRelevantMemories.ts`** — LLM-селектор релевантности: JSON-schema
  вывод, максимум 5, системный промпт «only include memories you are certain will be helpful …
  be selective», пустой результат — норма (абстейн первокласснен). Дедуп против уже
  показанных (`collectSurfacedMemories` сканирует транскрипт — компакция естественно
  сбрасывает), исключение файлов/тулов, уже находящихся в работе, бюджет `MAX_SESSION_BYTES`.
  Физическое скоупирование по каталогу проекта (`getAutoMemPath`); коммит 0ff1d1c — поиск
  каталогов по границам пути, не по префиксу имени (наш класс «чужая память утекла»).
  Prefetch как disposable параллельно основному запросу — релевантность НЕ добавляет латентности.
- **hermes**: ранжирование `final_score = relevance × trust_score` с полом `min_trust=0.3` и
  **временны́м распадом** `0.5^(age_days/half_life)` (`plugins/memory/holographic/retrieval.py`)
  — свежесть встроена в скоринг. Write-side гигиена: прерванные ходы НЕ синкаются и не
  прифетчатся («partial assistant output is not durable conversational truth — mirroring it
  pollutes future recall», `run_agent.py:3681`); `sanitize_context()` срезает уже-обёрнутые
  `<memory-context>`-блоки перед ре-инжестом; контекст-гейт записи (primary/subagent/cron —
  cron не пишет). Recall подаётся fenced-блоком «NOT new user input».

## Эскиз фаз

A. **Абстейн-гейт recall**: порог релевантности (или LLM-селектор по образцу openclaude,
   дешёвой моделью, с «пусто — норма»); recall из N кандидатов может вернуть 0. Метрика:
   доля прогонов с признанным-нерелевантным recall.
B. **Свежесть**: temporal decay в скоринге (half-life конфигурируемый) + «trust newest»
   инструкция в рендере recall-блока (кандидат из 021).
C. **Починка supersede** (открытый пункт 021): bounded-retry экстракции при не-JSON ответе /
   structured-output режим; raw-fallback помечать `slot=null` И исключать из recall-ранжира
   выше свежих слотовых фактов.
D. **Write-side гигиена**: не синкать отменённые/прерванные раны (сейчас `turn_synced` ставится
   только на completed — проверить cancel-путь); санитайзер против ре-инжеста recall-блоков;
   гейт контекста записи для субагентов/фоновых прогонов.
E. **Рендер-рамка**: recall-блок всегда с явной пометкой «справочная память, НЕ часть этого
   разговора; при конфликте с текущим диалогом приоритет у диалога» — прямо бьёт по симптому №2.
F. Приёмка: `clarify_when`-класс в составе полного свипа (не изолированно) стабильно PASS;
   стейл-факт кейс из dd9a5ee; Аргус-бенч без регрессий.
