# Conversation-first контракт хоста: история — массив сообщений, контекст — вложение

Дата создания: 2026-07-23 (из MeetScript B17). Статус: **proposed**.

Мотивация из живых данных: B17 — «сколько из этих шести?» разрешалось по retrieval-источникам,
а не по собственному перечислению ассистента, потому что хост собирал ОДИН составной RAG-промпт
с одним лишь последним вопросом: **истории разговора для модели не существовало вовсе**
(Phoenix: system + один user). Движковый `protect_recent_turns` (7d6dc3d) чинил другой слой —
движковую историю — и не мог помочь. Хост-фикс («Недавний диалог» текстовым блоком, 4 хода /
6000 симв.) закрыл симптом, но это паллиатив: история как текст в промпте не кэшируется
префиксно, не защищена от «протухания» при росте, и каждый хост изобретает её заново.
Оба референса решают структурно: **история всегда passed как массив сообщений; RAG/память/
стиринг инъецируются отдельными, помеченными каналами, не подменяя историю.**

## Reference-first

- **hermes**: инвариант «History is owned by the agent» (`gateway/stream_events.py:25-32`).
  Эфемерный контекст (prefetch памяти, plugin-контекст) компонуется в `api_content` ТЕКУЩЕГО
  user-хода на этапе API-вызова — оригинал в `messages` не мутируется, исторические ходы
  реплеятся байт-в-байт (стабильность префикса промпт-кэша, `conversation_loop.py:984-1021`);
  `reasoning_content` копируется назад для всех assistant-ходов (непрерывность рассуждений).
  Recalled-память — отдельный fenced-блок `<memory-context>` + «System note: NOT new user
  input» (`memory_manager.py:337-351`).
- **openclaude**: полный `Message[]` — единственный источник правды (`REPL.tsx:2942` →
  `query.ts:1349`); контекст — слоями (`prependUserContext`, attachment-сообщения
  `relevant_memories` как `<system-reminder>`). Компакция защищает хвост:
  `keepRecent: 5` у microcompact (`timeBasedMCConfig.ts`), tool-pair-safe диапазоны,
  `preservedSegment` для резюма.
- **openclaude eb72c77 — `requestOnlyMessages`**: первоклассный канал «видно модели в ЭТОМ
  запросе, но никогда не персистится, не компактится, не отдаётся тулам»; инвалидируется при
  любом переписывании истории (`query.ts:919,1873,1917`). Родился для interruption-correction
  («предыдущий ход прерван — трактуй новое сообщение как поправку»), но обобщается на любой
  эфемерный стиринг. У нас аналога нет: наш steering и RAG-обвязка едут внутри составного input.

## Эскиз фаз

A. **Движок**: канал эфемерного контекста в `AgentRunInput` (например,
   `request_only_context: list[ChatMessage]` или расширение `app_metadata`) — инъекция перед
   последним user-ходом на этапе сборки запроса, без записи в чекпойнт/журнал/историю;
   инвалидация при компакции. Покрыть протокольной гигиеной 018 (pair-integrity).
B. **Док-контракт для RAG-хостов** (`docs/host-conversation-contract.md`): история — всегда
   реальный массив ходов (включая ответы ассистента); retrieved-контекст — fenced-блок или
   attachment с явной пометкой «reference data, not user input»; условия, когда допустим
   composed-prompt (одноходовые джобы) и чем он платит (B17-класс). Ссылка из README.
C. **Миграция MeetScript** (фазовая, за гейтом): с составного промпта на
   messages + attachment-блоки (retrieval, обзор корпуса, память) — убирает и текстовый
   «Недавний диалог», и двойную конденсацию; ожидаемый бонус — префиксный кэш на истории.
D. Приёмка: B17-класс кейсов (анафора на собственное перечисление) + CEO-бенч без регрессий;
   замер cache-hit у провайдера до/после.
